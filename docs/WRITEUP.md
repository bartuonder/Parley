# Building Parley: what measuring an agent system taught me

Parley resolves customer support tickets with several cooperating model-driven agents: it looks up a customer's orders and subscriptions, finds the policy in force on the day, decides whether a refund or cancellation is allowed, asks a human when money is large, and writes the reply. The interesting part is not the agents; it is that every change had to survive a measurement. This page tells how the system is built and, mostly, where the measurements disagreed with my expectations.

## The problem

Support work looks like a good fit for language models and is easy to get subtly wrong. The answer depends on rules that change over time (the 14-day return window became 30 days on 1 September 2025), rules that conflict (a regional policy against a global one), records spread over several tables, and a customer who may be mistaken, insistent or hostile. A reply that sounds right while the database says otherwise is worse than no reply. So the system needed three things from the start: a backend that is the source of truth, a way to judge outcomes by what changed in that backend, and a way to repeat the judgment cheaply.

## The system in one page

A synthetic world stands in for the company: customers, orders, shipments, subscriptions, invoices and refunds in Postgres, 38 policy documents with versions, effective dates and deliberate conflicts, and a set of business rules in code that serve as the oracle. The rules and the policies are tied together by a test, so a policy cannot silently disagree with the rules that grade the agents.

A ticket goes through a LangGraph graph. A small model routes it to a billing, shipping or subscription specialist. The specialist investigates with read tools and a policy search (section chunks, MiniLM embeddings, a cross-encoder reranker and a date filter, chosen by an ablation over chunking, embedding, search mode and reranking). It cannot change anything: it can only propose a refund, a cancellation or a handover. A policy critic reviews the proposals, with deterministic rules first (a legal threat means a handover and nothing else; two refunds in the last 30 days plus a new request means a human) and a model check against the policy passages and the records the specialist saw. Only an approved plan is executed, by a separate step. A responder writes the reply from what actually happened, and a claim detector rewrites it once if it still promises something that did not occur. Refunds above $200 pause the graph at an interrupt; a decision in the console resumes it from its checkpoint.

Tools sit in one typed registry with read, write and risky permission levels, bound to the ticket sender, so a request about someone else's order is refused at the tool layer, not by the model's good behavior. Write operations are idempotent with keys derived from ticket, target and amount, and refunds serialize on a row lock (a threaded test showed that two refunds on one order both succeeded before the lock existed).

## Measuring

Each of the 140 scenarios builds its own small world and names the database diff that counts as success, a reference solution and the actions that must not happen. Four sets exist: 55 core, 31 held-out, 14 multi-turn dialogues played against an LLM customer, and 36 attacks. Success is "the final state matches", never "the reply looks good"; a calibrated judge grades reply quality separately. Because single runs swing by a scenario, decisions use repeated runs and pass^k (a scenario counts only if it passes every time). A regression gate compares each run with a committed baseline.

## What the measurements taught me

**Tuning on the evaluation set is visible in the numbers.** When the held-out set arrived, the graph that scored 100% on the core set scored 91.4% on it. After fixing what the new set found, held-out reached 99.2%. The 8.6 points are the measurable cost of having tuned on one set, and the held-out set is no longer untouched because I fixed two of its scenarios after a first run (and said so in the results).

**The critic is the part that matters.** An ablation of the graph's parts showed that removing the critic costs six points of task success on the core set, while the router and the reply rewrite showed no gain I could measure. The single agent was good (93.2% on core) and the graph better (99.5%), at about 1.4 to 1.8 times the cost and twice the latency, with a comparison that favors the graph because its prompts were written after reading the single agent's failures.

**Repeats catch what a single run hides.** Reading the customer's overview before the first model turn saved about 10% of the cost and looked fine in one run. Repeated gate runs showed two scenarios failing every time: with the data already in front of it, the model investigated less. It stayed as an option and the default went back. Similarly, three tempting economies lost: a smaller model for critic and responder (70.9% success, more calls, slower), a larger critic (double the cost, no gain) and a classifier router whose "accepted specialist" accuracy was 100% yet which sent a cancellation to billing, where the model answered with an offer. The measure I chose first (was the specialist acceptable?) was too generous to show the harm; the outcome measure caught it.

**Do not ask a model to be consistent about a pattern; write the rule.** The "two refunds in 30 days" fraud pattern was judged differently from run to run and caused a regression once guards were on. As a critic rule it passes in every run since.

**Security needs two numbers.** The backend already refuses most forbidden refunds, so counting only attacks that changed state hides how often the agent was fooled. I report whether the agent was manipulated (it tried a forbidden action) separately from whether the attack landed (state changed, another customer's data leaked, internals exposed). Without guards the single agent was manipulated in 19.4% of attack runs and harmed in 11.1%; the graph in 5.6% and 5.6%. With the guards on (data fencing with a per-request token, a rule-based scan of ticket and tool output, an egress check on replies, redaction of stored notes, a policy-integrity check, a refund-splitting limit and a critic that looks for injected instructions) no attack landed. The attack set was written by the same author as the defenses, one test-split attack was fixed after it failed and is disclosed as such, and 36 attacks cannot support more than "not seen". The per-guard ablation taught me something I had not expected: with the other guards on, removing any single one made no measurable difference except the policy-integrity check, the one defense against a corrupted index entry. Overlapping defenses hide each layer's value when you remove it alone, and 36 attacks, one run each, cannot rank the layers; I report the table and refuse to conclude that the other guards are redundant.

**Noise sets the tolerance, not the other way round.** Handover accuracy moved between 84.9% and 94.6% on the held-out set across runs of effectively the same code. A gate tolerance of five points flagged a regression that was noise; the tolerance is now ten, and the gate widens its allowance with the number of cases behind a metric (a metric with three expected writes cannot fail on one scenario). I would rather state the noise floor than pretend the gate is sharper than it is.

**Running the real thing finds what test worlds cannot.** The load test of the HTTP service showed it stalling under a burst: the graph uses synchronous database sessions inside async code, a burst exhausted the connection pool, and the blocked event loop could not release the connections. The fix is a bound on concurrent tickets with a pool sized from it, and tickets left running by a stopped process are failed on restart. Later, building the demo against the seeded world (hundreds of customers, not the small scenario worlds) showed the critic rejecting a correct refund three times because the evidence it was given was cut at 1,800 characters and the order's items fell off the end. Raising the limit took one ticket from 18.7 s and $0.0098 to 7.0 s and $0.0041. That is one observation, not a benchmark, but it is a real bug that the scenario worlds were too small to expose.

## Cost and speed

A ticket costs about $0.003 in model calls and takes about six seconds. The specialist loop is 70% of the cost and the critic 19%. The provider's prompt cache already serves 56% of the specialist's prompt tokens without any change, because tool definitions and the system prompt come first; the critic and responder prompts are shorter than the cache minimum. A semantic cache for policy search would save about 30 ms per ticket and sometimes returns a different best passage, so it is built, measured and left off. The ticket service handles 4.0 tickets/s on one machine with a simulated model at 0.3 s per call; with a real model the provider's rate limits become the ceiling.

## What I would not claim

The world is synthetic and the scenarios were written by one author; the labels were reviewed by one person; the same model family plays agent, critic and judge; prompts were tuned while looking at the scenarios; ATK-027 and SHP-002 fail in some runs; the console has one shared API key and no login; the service has not been deployed to a cloud host and was not load-tested against a real model. The results describe how the system behaves on this world. They are strong evidence that the engineering works (the harness, the gate, the traces, the guards) and weak evidence about any real customer base.

## What I would do next

Add attacks from someone who did not write the defenses; run the held-out and red-team sets on a second model family; make the graph's database access asynchronous so one process handles many tickets without a bound; add a login in front of the console and deploy the Compose stack to a host.
